## Context

Online play is host-authoritative: the host runs the one real `GameService`/rules engine; the guest runs a *passive* `GameService` replica wrapped by `NetworkedGameService`, whose mutating methods never touch rules locally — they become protocol commands sent to the host (`src/network/NetworkedGameService.ts`). The host pushes its own play and the guest's command results back as `{events, snapshot, pendingDecision}` bundles (`HostSession`/`GuestSession`, `src/network/HostSession.ts` / `GuestSession.ts`). The guest applies every bundle through `OnlineMatch.applyBundle` (`src/network/OnlineMatch.ts`), which today:

1. Replays the host's events onto the guest's local `eventBus` (drives animations, dialogs, dice log).
2. Overwrites the local replica's `GameState` from the bundle's `GameSnapshot` (`applySnapshotToTeams` + `Object.assign(replica.getState(), deserializeGameState(snapshot))`).
3. Emits a synthetic `PhaseChanged` if the phase/subPhase moved.
4. Emits `UI_SyncBoard` to reconcile board visuals.

`GameSnapshot` (`src/headless/serialization.ts`) is a JSON-safe projection of `GameState` plus teams; it does **not** carry `TurnManager`'s internal per-team turn counts, only `state.turn` (the *currently active* team's turn data).

Investigated three user-reported bugs, all specific to the guest/non-host view:

1. **"Ball on the wrong square, probably a seed issue."** Traced the actual dice/RNG path: `BounceOperation` and friends call `gameService.getDiceController()` only from inside `GameOperation`s that run exclusively as part of command execution (`declareAction`/`movePlayer`/`block`/etc.), all of which are intercepted by `NetworkedGameService` and turned into wire commands on the guest — the guest's own `RNGService`/`DiceController` is constructed (same `lobby.seed`, matching `game-sync-transport`'s hello contract) but **never consumes a roll**. Ball-landing coordinates for bounces/scatters/passes travel to the guest as literal payload fields on events like `PassFumbled` (`position`, `bouncePosition`) — not recomputed. So the seed hypothesis is wrong; both clients always agree on where the ball actually is. The actual bug is in *rendering*: `PlayPhaseHandler` registers `BallPlaced`/`BallPickup` handlers that call `scene.reconcileBallVisual()`, which derives the ball's rendered square from `gameService.getState()` at the moment the handler runs — **not** from the event payload. Because `applyBundle` replays events (step 1) *before* applying the snapshot (step 2), these handlers read the *previous* bundle's stale `ballPosition` when they fire, so the ball visually snaps to where it was one bundle ago. The `PlayerStatusChanged` handler has the same `reconcileBallVisual()`/`reconcilePlayerLocation()` call and the same latent bug for player-location rendering.
2. **"Turn counter never goes up for the non-host."** The scoreboard's per-team turn track (`ScoreBoard.tsx`, "Turn X of 6" plus six pips) reads `gameService.getTurnNumber(teamId)` for *both* teams. That method is `GameService.getTurnNumber` → `TurnManager.getTurnNumber(teamId)` → `this.turnCounts[teamId]`, a field private to each `GameService`/`TurnManager` instance. It is never part of `GameSnapshot`, so the guest's passive replica's own `TurnManager` — constructed once at match boot with both counts at `0` — is never touched again for the rest of the match; nothing in `applyBundle` calls `restoreTurnManagerState`. (The big banner `TurnIndicator` reads `state.turn.turnNumber` off the synced `GameState` and updates correctly off `TurnStarted`/state reads — this bug is specific to the scoreboard's per-team track, which is what "turn counter" refers to for a Blood Bowl player.)
3. **"Timer hitting zero doesn't end the turn properly."** `TurnClock` (`src/ui/pages/TurnClock.tsx`) force-ends the turn host-side by calling `gameService.endTurn()` directly (bypassing the protocol, same as the "End Turn" button — both are direct host-native calls, not commands). `GameService.endTurn()` just delegates to `turnManager.endTurn()`, which flips the active team and starts a fresh `state.turn`, but **never clears `state.activePlayer`**. Only `finishActivation()` clears it (after committing the declaration). If the clock fires while a player's declared once-per-turn action (Blitz/Pass/Hand-off/Foul) is already committed but the activation was never finished, `state.activePlayer` survives into the next team's turn. `GameService.declareAction()` refuses any new declaration while `state.activePlayer` is set and its `action` is in `ONCE_PER_TURN_ACTIONS` and committed (`"Cannot change the declared Action — <reason>."`) — so the *next* team's first `declareAction()` call is silently rejected. The turn did flip internally (`activeTeamId`, turn counter, clock deadline all moved on) but the new team cannot act, which reads exactly like "the timer expiring didn't end the turn."

None of the three share a single root cause — they are three independent gaps in what "ending a bundle"/"ending a turn" actually resets or transmits — but all three are the same *category* of bug: state that the guest (or the next-turn engine state) needs was silently left out of what gets synced/reset, so fixing them is three small, independent, well-scoped patches rather than one unifying rewrite. Bundling them in one change is purely because they were reported and triaged together.

## Goals / Non-Goals

**Goals:**
- Guest's rendered ball/status always matches the bundle it just applied — no stale-by-one-bundle visual state.
- Guest's per-team turn counter (scoreboard) tracks the host's actual per-team turn counts throughout the match, including across resync/reload.
- A clock-forced (or manual, mid-activation) `endTurn()` never leaves a stale `state.activePlayer` that blocks the next team's first action.
- Regression coverage at the `HeadlessGame`/`HostSession`/`GuestSession` level (per existing `__tests__/network/sessions.test.ts` patterns) — no requirement for two real browser clients.

**Non-Goals:**
- No change to how dice/RNG actually work — confirmed this was never the problem.
- No renegotiation of the wire protocol/envelope format beyond adding one optional field to `GameSnapshot`.
- Not fixing every possible `state.activePlayer` edge case beyond the force-end-turn path (e.g. this does not audit every other direct engine call for the same class of staleness beyond what's needed here).
- Not restructuring `applyBundle` beyond reordering its two existing steps.

## Decisions

**D1 — Reorder `applyBundle`: apply snapshot before replaying events.**
Swap the two top-level steps in `OnlineMatch.ts`'s guest `applyBundle` so the replica's `GameState` (`Object.assign(replica.getState(), deserializeGameState(snapshot))` + `applySnapshotToTeams`) is updated *before* the host's events are re-emitted on the local `eventBus`. Alternatives considered: (a) add an explicit ball/board reconciliation call inside the `UI_SyncBoard` handler's PLAY branch — rejected, because `reconcileBallVisual()`/`placeBallVisual()` kills in-flight tweens and snaps the sprite immediately, which would interrupt the smooth carry/bounce animations that already work correctly via event payloads (`animateBallAlong`, the `PassFumbled` bounce tween) — this would trade a positional bug for an animation regression, called on every bundle rather than just the ones that need it. (b) Make `reconcileBallVisual()` payload-driven instead of state-driven — rejected as a much larger change touching a widely-reused, currently-correct reconciliation helper used outside the online path too (setup, kickoff, local play, save/restore). Reordering is minimal, matches the two consumers of `pending`/state assignment already positioned after event replay in the current code (kept in the same relative order — only the state-apply step moves earlier), and does not change payload-driven animation handlers (`PlayerMoved`, `PassFumbled`) at all, since they never read `getState()`.

**D2 — Sync `TurnManager` state as an optional field on `GameSnapshot`, restored by the guest on every bundle.**
Add `turnManager?: TurnManagerState` to `GameSnapshot` (reusing the existing `TurnManagerState` type already used by local `MatchSave`), populated in `HeadlessGame.snapshot()` via `this.ctx.gameService.captureTurnManagerState()` (a method that already exists and is already used for local save/restore — see `ServiceContainer.ts`/`GameScene.ts`). In `OnlineMatch.ts`'s guest `applyBundle`, call `replica.restoreTurnManagerState(snapshot.turnManager)` whenever present, right alongside the existing state `Object.assign`. Alternatives considered: (a) have the guest derive turn counts locally by counting `TurnStarted` events over the match — rejected, fragile across resync/reload (a resync carries no event history) and duplicates logic that already exists correctly on `TurnManager`. (b) Widen `state.turn` itself to carry both teams' counts — rejected, `state.turn` is the *current* activation record (one team, reset every `startTurn`); conflating it with the durable per-team counters changes its shape for every consumer (headless CLI, saves, AI JSON mode) for no benefit over reusing the already-existing, already-serializable `TurnManagerState`.

**D3 — `GameService.endTurn()` finalizes a dangling `state.activePlayer` before delegating to `TurnManager.endTurn()`.**
Mirror the same commit-then-clear pattern `finishActivation()` already uses: `if (this.state.activePlayer) { this.playerActionManager.commitAction(this.state.activePlayer.id); this.state.activePlayer = null; }`, then call `this.turnManager.endTurn()`. `commitAction` is documented idempotent ("safe to call from every trigger point... without checking which one actually fired first") so this is safe whether the declaration was already committed, uncommitted, or absent. Alternatives considered: (a) special-case the clock's forced end-turn only (e.g. a new `IGameService.forceEndTurn()`) — rejected, the exact same staleness can happen from the ordinary "End Turn" button clicked mid-activation (not online-specific), and a second code path duplicates the fix instead of closing the gap once at its actual source (`GameService.endTurn()`). (b) Refuse to end the turn while `state.activePlayer` is set — rejected, contradicts `turn-timer`'s existing "host ends the turn on their behalf... so a player cannot lock the game open indefinitely" requirement; the whole point of the clock is to force through an unresponsive/indecisive player.

## Risks / Trade-offs

- [D1: reordering could theoretically surface a handler that relied on the old "state not yet updated" timing] → Audited every `PlayPhaseHandler`/`GameScene` listener that fires on events crossing the wire (excluding `UI_INTENT_EVENTS`, which never replay on the guest); the only `getState()`-reading handlers found are the ball/status reconciliation ones this change targets, and they *want* fresh state. Regression test plays a full networked match (existing `sessions.test.ts` pattern) to catch any behavioral break.
- [D2: `TurnManagerState` also holds `driveKickingTeamId`/`firstHalfKickingTeamId`/`turnoverInProgress` — restoring it wholesale on the guest could fight with fields the guest derives another way] → Reviewed `GameState`/`GameSnapshot`: none of those three fields are otherwise synced or read independently on the guest for anything other than what `TurnManager` itself needs (kickoff sub-phase choice, half-turn accounting), so restoring the host's authoritative copy wholesale is strictly a superset fix, not a conflict.
- [D3: forcibly committing a barely-declared action (e.g. a Blitz with zero movement spent) at turn end spends the team's Blitz for that turn, same as it would if the player had simply clicked "End Activation"] → This matches existing single-player/local behavior already documented in `finishActivation()`'s own comment ("a Blitz ended without moving or rolling still spends the team's Blitz") — no new rule, just applying the same finalization on the forced path that already happens on the normal path.

## Migration Plan

Pure bugfix, no data migration. `GameSnapshot.turnManager` is optional/additive — old snapshots (e.g. cached `localStorage` guest snapshots, in-flight bundles from a not-yet-updated host) simply omit it and the guest's `applyBundle` skips the restore call, matching the file's existing "absent on pre-feature saves" convention used for `driveEffects`/`bribes`/etc.

## Open Questions

None — all three root causes were confirmed by reading the actual code paths (not speculative), and each fix is additive/localized enough not to need a design review checkpoint.
